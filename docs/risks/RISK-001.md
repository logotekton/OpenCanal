# RISK-001 — opencanal 플랫폼 전체 (v0 설계 기준선)

> NDSH 부록 B-2 양식. 변경 단위가 아니라 **서비스 전체의 기준 위험**을 적는다. 이후 변경마다 RISK-00N을 따로 연다.

- 연결: START.md v0 얇은 조각
- 서비스 범위: **최종 R2 / v0 R0** (로컬, 합성 데이터와 오너 본인 데이터만)
- P 실패 가능성: 2 — 멀티테넌트 그래프, LLM 입력, 티어 게이트처럼 실수하기 쉬운 표면이 많다
- I 실패 영향: 3 — 개인 두뇌에는 사적인 생각, 회사 정보, 제3자 이름이 섞여 있다
- D 발견 난이도: 2 — 서브브레인에 숨은 민감 정보나 다른 사용자 데이터 누출은 정상 테스트로 드러나지 않는다

## 피해

- **영향받는 사람:** 서브브레인을 공개한 사용자, 그리고 서브브레인 안에 이름이 나오는 제3자
- **데이터·돈·업무:** 개인 지식, 회사 기밀, 향후 구독료
- **피해 반경:** 한 서브브레인의 비공개 노드가 새면 그 서브브레인을 연 모든 커널의 참여자에게 퍼진다. 델타브레인은 복사되어 남는다

## 강제 상향

- [x] 인증·권한·tenant·관리자 — 사용자별 서브브레인 가시성, 티어 게이트
- [x] 개인정보·민감정보 — secondbrain 내용 자체가 개인정보일 수 있다
- [x] 결제·환불·원장 — 티어 과금 (v0 범위 밖, 설계만)
- [ ] DB migration·대량 수정 — v0은 새 DB
- [ ] secret·CI·배포·backup — v0 로컬. 배포할 때 다시 연다
- [x] 외부 발송·삭제·구매 agent — 사용자 LLM이 MCP로 서브브레인 공개와 철회 같은 **쓰기**를 한다 (T2)
- [ ] 물리 hazard — 해당 없음

## opencanal에만 있는 실패 방식과 통제

| ID | 실패 방식 | 통제 (v0에서 구현) | 검증 |
|---|---|---|---|
| F1 | 남의 비공개 서브브레인이나 철회된 서브브레인이 검색, 커널, 델타브레인에 나온다 | 모든 조회 경로에서 서버가 가시성 검사. 기본은 거부 | A/B 부정 시험 (search, open, deltabrain, 직접 ID 호출) |
| F2 | 서브브레인에 의도하지 않은 민감 정보가 들어간다 (원문, 로컬 파일 경로, 사람 이름) | 서브브레인은 구조와 짧은 요약만. `source_url`과 경로 필드는 가져올 때 제거. 공개 전에 미리보기를 보여주고 오너가 확인 | 경로·이메일·전화번호 패턴 fixture로 차단되는지 확인 |
| F3 | 남의 서브브레인 속 문장이 내 LLM에 지시로 작동한다 (prompt injection) | 서브브레인 내용은 항상 `untrusted_data`로 감싸서 반환. 커널 세션에서 쓰기 도구는 `canal_submit` 하나뿐. 플랫폼은 서브브레인 내용을 실행하지 않는다 | "이전 지시 무시" 문구를 심은 공격 서브브레인 fixture |
| F4 | 합성기가 출처 없는 노드를 지어낸다 | 제출할 때 모든 노드·엣지의 출처가 이번 커널에서 연 서브브레인 버전을 가리키는지 서버가 검증. 아니면 거부 | 가짜 출처, 다른 커널의 서브브레인을 인용한 제출 → 거부 |
| F5 | 매칭이 비슷한 사람만 붙여서 반향실을 만든다 | 관련성(질의 기준)과 거리(호스트 기준)를 함께 쓰는 매칭 | 커널마다 다른 도메인 서브브레인이 1개 이상 들어가는지 확인 |
| F6 | 티어 게이트를 도구 숨김으로만 구현해서 직접 호출로 우회된다 | 도구 목록 필터링과 **별도로** 매 호출마다 서버에서 티어 검사 | 낮은 티어 토큰으로 숨겨진 도구를 직접 호출 → 거부 |
| F7 | 서브브레인을 철회해도 델타브레인에 파생 내용이 남는다 | 철회하면 새 커널에서 즉시 제외. 기존 델타브레인 처리 정책은 미결 → DECISIONS | 철회 후 search와 open에서 0건 |
| F8 | MCP URL 토큰이 새서 다른 사람이 접근한다 | 토큰 재발급과 폐기, 로그에서 토큰 마스킹 | 폐기한 토큰으로 호출 → 거부 |
| F9 | 사용자 LLM 비용이나 플랫폼 호출이 폭주한다 | 커널당 서브브레인 수와 노드 수 상한, 사용자별 호출 한도 | 상한을 넘는 요청 → 잘림 또는 거부 |
