# DECISIONS — opencanal

> NDSH B-13. 결정마다 고른 것, 포기한 것, 재검토 조건을 남긴다.
> 상태 표기: **확정** / **제안** (오너 답 대기) / **미결**

---

## D-001 기술 스택 — 제안

- **선택:** Python 3.11+, FastAPI, 공식 `mcp` SDK의 FastMCP(streamable HTTP, `/mcp/{token}`에 마운트), v0 저장소는 SQLite. 웹은 나중에 React와 Vite.
- **근거:** 형제 프로젝트 `modular-ontology`가 이미 같은 구성이다. FastAPI에 FastMCP를 마운트하고, 사용자별 MCP 토큰 URL을 발급하고, 토큰에서 접근 범위를 유도하고, 팩 가시성을 필터링한다. 오너가 이미 운영해 본 패턴을 그대로 쓴다.
- **차이:** modular-ontology는 도구 숨김과 가시성 필터를 쓴다. opencanal은 여기에 **매 호출 서버측 티어 검사**를 더한다 (RISK F6).
- **포기:** Node 기반 MCP 서버, 처음부터 Postgres와 그래프 DB를 쓰는 안. v0 규모에서는 운영 부담만 늘어난다.
- **재검토:** 동시 사용자가 생기거나 R1으로 승격할 때 Postgres로 옮긴다. 벡터 매칭을 도입할 때 pgvector를 검토한다.

## D-002 서브브레인 정규 스키마 — 제안

- OpenCrab 응답에 이미 있는 provenance 필수 필드(`source_locator`, `external_id`, `collected_at`, `derived_by`, `derivation_version`)에 맞춘다. 새 체계를 따로 만들지 않는다.
- 노드: `id`, `label`, `type`, `summary`(짧은 요약, 상한 있음), `tags[]`
- 엣지: `id`, `source`, `target`, `relation`, `summary?`
- 서브브레인 메타: `subbrain_id`, `version`, `owner`, `title`, `domains[]`, `visibility`, `published_at`, `content_hash`
- 가져올 때 원문 청크, `source_url`, 로컬 경로를 제거한다 (Q2).

## D-003 매칭 = 관련성(질의) × 거리(호스트) — 제안

- PROJECT.md의 핵심 설계 명제를 따른다. v0은 태그와 어휘 기반으로 관련성을 보고, 도메인 군집으로 거리를 본다. 임베딩은 v1에서 넣는다.
- **포기:** 순수 유사도 매칭. 반향실을 플랫폼 규모로 재생산한다.

## D-004 MCP 도구 지도와 티어 — 계획만 (확정은 기능 완성 뒤)

| 도구 | 행동 | NDSH 도구 등급 | Free | Pro | Expert |
|---|---|---|:---:|:---:|:---:|
| `subbrain_search` | 공개 서브브레인 검색 (메타와 요약) | T0 | ✓ | ✓ | ✓ |
| `subbrain_publish` | 내 서브브레인 버전 공개 | T2 (되돌릴 수 있는 내부 쓰기) | 1개 | N개 | N개 |
| `subbrain_revoke` | 내 서브브레인 철회 | T2 | ✓ | ✓ | ✓ |
| `canal_open` | 질의로 커널 열기 → 서브브레인 묶음 반환 | T1 | 월 k회, 서브브레인 3개 | 상향 | 상향 |
| `canal_submit` | 델타브레인 제출 | T2 | ✓ | ✓ | ✓ |
| `deltabrain_get` / `deltabrain_list` | 결과 조회 | T1 | ✓ | ✓ | ✓ |
| `canal_synthesize` | 플랫폼측 중립 합성 (Q1-B나 C를 고를 때) | T2 + 비용 | — | — | ✓ |

- 티어는 **도구 목록 필터링과 매 호출 서버측 검사를 둘 다** 한다. 숨김은 편의일 뿐 권한이 아니다.
- 사용자와 tenant는 인자로 받지 않고 토큰에서 유도한다.
- 수치(N, k)는 기능 완성 뒤 정한다.

## 설계 질문 Q1~Q4 (2026-10-06 오너 답변 반영)

### Q1. 합성기는 누가 돌리는가? — **확정: A부터** (2026-10-06)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | **질의한 사람의 LLM**이 MCP로 서브브레인을 받아 합성하고 결과를 제출한다 | "개인 LLM이 MCP로 소통"과 맞다. 플랫폼 추론비가 0이다. 지금 바로 만들 수 있다 | 합성하는 쪽이 '내' LLM이라 내 메모리와 프롬프트가 섞인다. **오염 문제가 합성 단계에서 다시 생긴다** |
| B | 플랫폼이 **고정된 중립 프로토콜**로 합성한다 | 오염 명제와 가장 잘 맞는다. 품질이 일정하다 | 플랫폼 LLM 비용이 든다. 플랫폼이 모든 서브브레인을 LLM 공급자에게 보낸다 (외부 처리자가 생긴다) |
| C | 플랫폼이 서브브레인마다 **그 서브브레인만 아는 대리 에이전트**를 세워서 서로 질의하게 하고, 그 과정을 그래프로 남긴다 | "두뇌끼리 커뮤니케이션"에 가장 가깝다 | 비용이 가장 크다. 평가가 어렵다 |

**확정:** 합성기를 교체 가능한 단계로 만든다. v0은 **A**로 시작하고, A를 쓸 때는 클라이언트에게 새 컨텍스트에서 플랫폼이 준 프로토콜로 합성하라고 요구한다. 합성기 종류는 출처에 기록한다. **B나 C는 상위 티어 기능 후보**로 둔다.

### Q2. 서브브레인에 무엇이 들어가는가? — **확정: 구조와 짧은 요약만** (2026-10-06)

**확정:** 노드와 엣지 구조, 노드별 짧은 요약(예: 280자 이하), 태그만 넣는다. 원문 텍스트, 출처 URL, 파일 경로는 넣지 않는다.
**이유:** 유출 피해가 줄고 prompt injection이 들어올 표면도 줄어든다. OpenCrab 결과에는 `C:\Logotekton\...` 같은 로컬 경로가 실제로 들어 있다. 이런 값은 가져올 때 지운다.

### Q3. 델타브레인은 누가 받는가? — **확정: 참여자 전원, 대칭 동의** (2026-10-06)

- 오너 원문은 "각 사용자들이 얻어가는 결과물"이다. 참여자 전원이 받는 쪽으로 읽힌다.
- 그러면 **호스트 서브브레인도 참여자들에게 노출**된다. 그래서 호스트도 커널에 참여할 수 있는 서브브레인만 호스트로 쓸 수 있어야 한다.
- **확정:** 참여자 전원이 받는다. 서브브레인을 공개할 때 "커널 참여자에게 노출된다"는 데 동의를 받고, 호스트 서브브레인에도 똑같이 적용한다. 대칭 동의다.
- **확정 (Q5, 2026-10-06):** 서브브레인을 철회해도 이미 만든 델타브레인의 파생 노드는 **유지**한다. 철회한 사람 표시를 남길지는 Oracle self-test 5에서 정한다.

### Q4. 첫 가져오기 소스는? — 제안 (기본값으로 진행)

**제안:** 정규 서브브레인 JSON을 먼저 정의한다. 첫 변환기는 **OpenCrab 팩**용으로 만든다. 오너 두뇌가 거기 있고, `opencrab_list_nodes`와 `opencrab_list_edges`로 읽을 수 있다. Obsidian 볼트 변환기는 그다음이다.

## D-005 사용자가 삭제해도 서버는 ID로 보관한다 — 오너 결정 (2026-10-06) · R2 전 확인 필요

**오너 결정:** 사용자가 서브브레인이나 델타브레인을 삭제해도, 사용자별 서브브레인 목록과 델타브레인 결과는 ID를 붙여 백업용으로 서버에 모두 보관한다.

**v0 구현:**

- 상태: `draft → published → revoked → user_deleted`.
- `user_deleted`는 tombstone(삭제 표시)이다. 행을 지우지 않고 사용자용 도구에서만 감춘다 (Oracle NEVER-03).
- 보관된 자료는 운영자용 복구 경로로만 접근한다. 접근할 때마다 감사 로그를 남긴다. MCP 도구로는 열지 않는다.

**R2 공개 전에 풀어야 할 충돌 — 지금 막는 건 아니다:**

1. **정직한 표기.** 실제로 지우지 않으면서 화면이나 도구에 "삭제"라고 쓰면 사용자를 속이게 된다. 도구와 UI 문구는 "내 목록에서 제거 (서버 보관)"처럼 실제 동작대로 쓰고, 이용약관과 처리방침에도 같은 내용을 고지한다.
2. **개인정보 삭제 의무.** 서브브레인은 계정에 연결된 개인 저작물이다. 그래서 개인정보일 수 있고 제3자 이름이 들어 있을 수도 있다.
   - NDSH 부록 G-1은 이용자의 열람·정정·삭제·처리정지 요청을 실제로 처리할 수 있어야 한다고 요구한다.
   - 10장은 "모든 데이터를 무기한 남기지 않는다", 법적 보존이 필요한 자료라도 근거·기간·접근 제한·분리 보관을 명시하라고 한다.
   - 따라서 다음 세 가지가 필요하다.
     - 보관 기간
     - 법적 삭제 요청과 탈퇴 때 쓸 **영구 삭제 경로**
     - 백업을 복원한 뒤 삭제 대상을 다시 지우는 절차
   - 적용 법(한국 개인정보보호법, 해외 이용자가 있다면 GDPR 등)은 출시 전에 전문가에게 확인한다.
3. **노출 위험이 커진다.** 오너가 꼽은 실패 1순위는 "서브브레인 노출"이다. 무기한 보관하는 백업은 유출되었을 때 피해 범위를 키운다. 백업은 분리 저장하고, 접근 권한을 최소로 두고, 암호화한다.

**재검토:** R1으로 승격하기 전에 보관 기간과 영구 삭제 경로를 정한다. 그 전에는 실제 타인 데이터를 받지 않는다.
