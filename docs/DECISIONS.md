# DECISIONS — opencanal

> NDSH B-13. 결정마다 고른 것, 포기한 것, 재검토 조건을 남긴다.
> 상태 표기: **확정** / **제안** (오너 답 대기) / **미결**

---

## D-001 기술 스택 — 확정 (2026-10-06)

- **선택:** Python 3.12, FastAPI, 공식 `mcp` SDK(1.30)의 FastMCP(streamable HTTP, `/mcp/{token}`), v0 저장소는 SQLite, 암호화는 `cryptography`. 웹은 나중에 React와 Vite.
- **근거:** 형제 프로젝트 `modular-ontology`와 같은 구성이다. FastAPI에 FastMCP를 마운트하고 사용자별 MCP 토큰 URL을 발급한다.
- **형제 프로젝트와 다르게 하는 것:**
  - 토큰은 **해시만** 저장한다 (형제는 평문).
  - 토큰이 없으면 **거부한다** (형제는 기본 범위로 열린다).
  - 티어는 도구 목록 필터링에 더해 **매 호출 서버측 검사**를 한다.
- **포기:** Node 기반 MCP 서버, 처음부터 Postgres와 그래프 DB를 쓰는 안.
- **재검토:** 동시 사용자가 생기거나 R1으로 승격할 때 Postgres로 옮긴다. 임베딩 매칭을 넣을 때 pgvector를 검토한다.

## D-002 서브브레인 정규 스키마 — 제안

- OpenCrab 응답에 이미 있는 provenance 필수 필드(`source_locator`, `external_id`, `collected_at`, `derived_by`, `derivation_version`)에 맞춘다. 새 체계를 따로 만들지 않는다.
- 노드: `id`, `label`, `type`, `summary`(짧은 요약, 상한 있음), `tags[]`
- 엣지: `id`, `source`, `target`, `relation`, `summary?`
- 서브브레인 메타: `subbrain_id`, `version`, `owner`, `title`, `domains[]`, `visibility`, `published_at`, `content_hash`
- 가져올 때 원문 청크, `source_url`, 로컬 경로를 제거한다 (Q2).

## D-003 매칭 — 관련도 하한은 확정, 다양성 기준은 미결

- **확정:** 질의 관련도 τ 미만은 넣지 않는다. 관련된 것이 없으면 빈 커널이다 (Oracle MUST-M1, NEVER-08). 주제 없는 질의는 호스트 서브브레인 전체를 질의로 쓴다 (MUST-M3).
- **미결:** 커널링 대상을 고르는 기준. 오너는 "더 고민"이라고 답했다 (self-test 2). PROJECT.md의 "관련성 × 거리" 명제는 가설로 남긴다.
- **v0 구현:** 매칭 전략을 교체할 수 있게 만든다. `relevance_plus_diversity`(기본)와 `relevance_only` 두 전략을 두고 `config/matching.json`에서 고른다. 오너가 후보와 점수를 직접 보며 기준을 연구할 수 있게 `match_explain` 도구를 둔다.
- **v0 관련도:** 태그·라벨·요약의 어휘 겹침으로 잰다. 임베딩은 v1에서 넣는다.

- 티어는 **도구 목록 필터링과 매 호출 서버측 검사를 둘 다** 한다. 검사는 전송 계층과 독립된 한 곳에서 한다.
- 사용자는 인자로 받지 않고 토큰에서 유도한다.
- **삭제 도구는 없다** (D-005).

## 설계 질문 Q1~Q4 (2026-10-06 오너 답변 반영)

### Q1. 합성기는 누가 돌리는가? — **확정: A부터** (2026-10-06)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | **질의한 사람의 LLM**이 MCP로 서브브레인을 받아 합성하고 결과를 제출한다 | "개인 LLM이 MCP로 소통"과 맞다. 플랫폼 추론비가 0이다. 지금 바로 만들 수 있다 | 합성하는 쪽이 '내' LLM이라 내 메모리와 프롬프트가 섞인다. **오염 문제가 합성 단계에서 다시 생긴다** |
| B | 플랫폼이 **고정된 중립 프로토콜**로 합성한다 | 오염 명제와 가장 잘 맞는다. 품질이 일정하다 | 플랫폼 LLM 비용이 든다. 플랫폼이 모든 서브브레인을 LLM 공급자에게 보낸다 (외부 처리자가 생긴다) |
| C | 플랫폼이 서브브레인마다 **그 서브브레인만 아는 대리 에이전트**를 세워서 서로 질의하게 하고, 그 과정을 그래프로 남긴다 | "두뇌끼리 커뮤니케이션"에 가장 가깝다 | 비용이 가장 크다. 평가가 어렵다 |

**확정:** 합성기를 교체 가능한 단계로 만든다. v0은 **A**로 시작하고, A를 쓸 때는 클라이언트에게 새 컨텍스트에서 플랫폼이 준 프로토콜로 합성하라고 요구한다. 합성기 종류는 출처에 기록한다. **B나 C는 상위 티어 기능 후보**로 둔다.

### Q2. 서브브레인에 무엇이 들어가는가? — **확정: 구조와 짧은 요약만** (2026-10-06)

**확정:** 노드와 엣지 구조, 노드별 짧은 요약(예: 280자 이하), 태그만 넣는다. 원문 텍스트, 출처 URL, 파일 경로는 넣지 않는다.
**이유:** 유출 피해가 줄고 prompt injection이 들어올 표면도 줄어든다. OpenCrab 결과에는 `C:\Logotekton\...` 같은 로컬 경로가 실제로 들어 있다. 이런 값은 가져올 때 지운다.

### Q3. 델타브레인은 누가 받는가? — **확정: 참여자 전원, 대칭 동의** (2026-10-06)

- 오너 원문은 "각 사용자들이 얻어가는 결과물"이다. 참여자 전원이 받는 쪽으로 읽힌다.
- 그러면 **호스트 서브브레인도 참여자들에게 노출**된다. 그래서 호스트도 커널에 참여할 수 있는 서브브레인만 호스트로 쓸 수 있어야 한다.
- **확정:** 참여자 전원이 받는다. 서브브레인을 공개할 때 "커널 참여자에게 노출된다"는 데 동의를 받고, 호스트 서브브레인에도 똑같이 적용한다. 대칭 동의다.
- **확정 (Q5, 2026-10-06):** 서브브레인을 비공개로 바꿔도 이미 만든 델타브레인의 파생 노드는 **유지**한다. 그 주인의 표시는 암호화한다 (D-006).

### Q4. 첫 가져오기 소스는? — 제안 (기본값으로 진행)

**제안:** 정규 서브브레인 JSON을 먼저 정의한다. 첫 변환기는 **OpenCrab 팩**용으로 만든다. 오너 두뇌가 거기 있고, `opencrab_list_nodes`와 `opencrab_list_edges`로 읽을 수 있다. Obsidian 볼트 변환기는 그다음이다.

## D-005 "삭제" 대신 공개/비공개, 서버는 모두 보관 — 오너 결정 (2026-10-06)

**오너 결정:**

- 사용자에게는 삭제 동작이 없다. 서브브레인은 **공개/비공개** 두 상태뿐이다.
- 서버는 사용자별 서브브레인 목록, 모든 서브브레인 버전, 델타브레인 결과를 ID로 보관한다.
- 보관 기간과 영구 삭제 경로는 공개 출시 전에 정하고 전문가에게 확인한다 (오너 "오케이").
- 백업은 분리 보관하고 암호화한다 (오너 "암호화 굳").

**v0 구현:**

- 상태: `private`(비공개, 가져온 직후 기본값) ↔ `public`(공개).
  - 공개 → 비공개로 바꾸면 검색과 새 커널에서 빠진다.
  - 기존 델타브레인의 파생 노드는 유지한다 (Q5).
  - 주인은 자기 목록에서 계속 본다.
- 공개하려면 가져올 때 받은 미리보기 `content_hash`를 확인값으로 보내야 한다. 정제 결과를 보고 확인하는 단계를 건너뛰지 못한다.
- 백업: `opencanal backup` / `opencanal restore`. Fernet으로 암호화한다. 키 파일은 0600 권한이고 gitignore한다 (Oracle MUST-E1).
- 표기: 사용자에게 보이는 말은 "공개", "비공개"뿐이다. "삭제", "철회"는 쓰지 않는다.

**공개 출시(R1/R2) 전에 할 일 — TASK-002로 분리:**

1. 보관 기간을 정한다.
2. 법적 삭제 요청과 탈퇴 때 쓸 **운영자용 영구 삭제 경로**를 만든다. 백업에서 복원한 뒤 삭제 대상을 다시 지우는 절차도 포함한다.
3. 약관과 처리방침에 "비공개로 바꿔도 서버에 보관된다"를 고지한다.
4. 적용 법(한국 개인정보보호법, 해외 이용자가 있으면 GDPR 등)을 전문가에게 확인한다.

이 네 가지는 v0 개발을 막지 않는다. 다만 끝나기 전에는 실제 타인 데이터를 받지 않는다.

## D-006 비공개 기여자 표시는 암호화 — 오너 결정 (2026-10-06)

- 기존 델타브레인에 지금은 비공개인 서브브레인에서 온 내용이 있으면, 그 주인이 아닌 참여자에게는 주인 자리에 `"비공개 기여자"`와 암호화 토큰만 보인다.
- 토큰은 AES-SIV(결정적 인증 암호화)로 `owner_id|deltabrain_id`를 암호화한 값이다.
  - 같은 델타브레인 안에서는 값이 같아서 "같은 기여자"인지 알 수 있다.
  - 델타브레인이 다르면 값이 달라서 여러 결과를 엮어 추적할 수 없다.
  - 서버 키로만 복호화된다.
- 키는 마스터 키 하나에서 HKDF로 용도별로 나눈다 (기여자 토큰용, 백업용).

## D-007 커널 규칙 — 플래너 제안, 오너 확인 대기

- **대칭 동의 강제:** 호스트 서브브레인이 공개 상태여야 커널을 열 수 있다 (Oracle MUST-C1). 남의 두뇌를 읽으려면 내 것도 보여야 한다.
- **호스트만 제출:** 델타브레인은 호스트(의 LLM)만 제출한다. 참여자는 받기만 한다 (MUST-C2).
- **후보 제외:** 호스트 본인의 다른 서브브레인은 후보가 아니다 (MUST-M4).
- **실패 시 차감 없음:** 관련 서브브레인이 없으면 커널을 만들지 않고 월 커널 수도 차감하지 않는다 (NEVER-08).
