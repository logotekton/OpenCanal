> NDSH 부록 B-4 양식. 이 문서가 v0의 정답 기준이다.

## 3. 품질 판정은 세 층으로 한다

| 층 | 판정자 | 하는 일 | 실패하면 |
|---|---|---|---|
| L1 결정론 검증 | 서버의 `canal_submit` 검증기 | 구조, 출처, 질의 연결, 창발, 새로움, 금지어를 검사한다 | **제출 거부.** 모든 위반을 이유 코드와 함께 한 번에 돌려준다 |
| L2 사람 라벨 | 오너 (`deltabrain_rate`) | 창발 엣지마다 새로움·타당성·쓸모를 0/1로 라벨한다 | 매칭이나 합성 프로토콜을 다시 설계한다 |
| L3 LLM Judge | 보조 | L2 라벨과 일치도를 먼저 잰다 | v0에서는 쓰지 않는다 |

L1은 **명백히 무의미한 것을 걸러내는 하한**이다. L1을 통과했다고 좋은 델타브레인인 것은 아니다.

## 4. 델타브레인 구조 정의 (검증기가 기대하는 모양)

- 노드 `kind`
  - `query`: 질의 노드. 정확히 1개. **출처 규칙에서 면제된다.**
  - `source`: 입력 서브브레인의 노드를 앵커로 가져온 것. 출처 정확히 1개. 라벨은 인용한 노드의 라벨과 같아야 한다.
  - `new`: 합성기가 만든 노드. 출처 2개 이상.
- 출처 참조 `ProvRef` = (`subbrain_id`, `version`, `node_id`)
- 엣지의 **유효 출처** = 양 끝 노드의 출처 ∪ 엣지에 직접 적은 출처
- **창발 엣지** = 유효 출처의 **주인(owner)이 2명 이상**인 엣지
- **호스트에 닿는 엣지** = 유효 출처에 호스트 서브브레인을 가리키는 참조가 있는 엣지

## 5. 핵심 기준표

### 5.1 델타브레인 품질 — L1 결정론 검증

| ID | 검사 | 거부 코드 |
|---|---|---|
| MUST-Q1 | `query`를 뺀 모든 노드에 출처가 있다. 모든 참조는 **이번 커널에 들어간** 서브브레인 버전을 가리키고, 그 버전에 실제로 있는 노드를 가리킨다. `new` 노드는 참조가 2개 이상이다 | `PROVENANCE_MISSING` / `PROVENANCE_OUT_OF_CANAL` / `PROVENANCE_INVALID` |
| MUST-Q2 | `query` 노드가 정확히 1개 있고, 모든 노드가 질의 노드에서 무방향 3홉 안에 있다 | `QUERY_NODE_COUNT` / `OFF_QUERY_NODE` |
| MUST-Q3 | 창발 엣지가 1개 이상 있고, 그중 1개 이상은 호스트 서브브레인에 닿는다 | `NO_EMERGENCE` / `HOST_NOT_TOUCHED` |
| MUST-Q4 | 엣지 관계는 통제 어휘(§5.2)만 쓴다. 창발 엣지에는 `rationale`(정규화 후 40~400자)이 있다 | `RELATION_NOT_ALLOWED` / `RATIONALE_MISSING` |
| MUST-Q5 | `new` 노드의 정규화 라벨이 커널 입력 서브브레인의 어떤 라벨과도 같지 않다. 양 끝이 `source`인 창발 엣지가 입력에 이미 있는 엣지를 그대로 옮긴 것이 아니다 | `NOT_NOVEL` |
| MUST-Q6 | `new` 노드 라벨이 금지 일반어(`config/generic_terms.txt`)만으로 이뤄지지 않는다 | `GENERIC_LABEL` |
| MUST-Q7 | 창발 엣지 중 정규화한 `rationale`이 다른 엣지와 똑같은 엣지의 비율이 20% 이하다 | `TEMPLATED_RATIONALE` |
| MUST-Q8 | 노드 60개 이하, 엣지 120개 이하 | `TOO_LARGE` |
| MUST-Q9 | `source` 노드의 라벨이 인용한 노드의 라벨과 정규화 기준으로 같다 | `SOURCE_MISMATCH` |
| MUST-Q0 | 스키마: 노드 ID 중복 없음, 엣지 양 끝이 존재하는 노드, 필수 필드 존재 | `SCHEMA_INVALID` |

**정규화** = 유니코드 NFKC, 소문자, 앞뒤 공백 제거, 연속 공백을 하나로, 구두점 제거.

### 5.2 엣지 관계 통제 어휘 (v0)

| 관계 | 뜻 |
|---|---|
| `applies_to` | A의 방법·원리를 B의 문제에 적용할 수 있다 |
| `analogous_to` | 구조가 대응한다 (무엇이 무엇에 대응하는지 rationale에 쓴다) |
| `contradicts` | A가 B의 전제나 결론을 반박한다 |
| `extends` | A가 B를 확장하거나 일반화한다 |
| `requires` | A가 성립하려면 B가 필요하다 |
| `alternative_to` | A가 B를 대체할 수 있다 |
| `explains` | A가 B의 원인·기제를 설명한다 (인과를 단정하지 않는다) |
| `risk_for` | A가 B의 실패·위험 요인이 된다 |

`related_to`, `관련있다`, `연결된다`, `시너지` 같은 무내용 관계는 어휘에 없으므로 `RELATION_NOT_ALLOWED`다.

### 5.3 델타브레인 품질 — L2 사람 라벨

| ID | 기준 | 판정 |
|---|---|---|
| HUMAN-01 | 창발 엣지마다 **새로움**(내 두뇌만으로는 안 나왔을 연결), **타당성**(rationale이 말이 된다), **쓸모**(질의에 실제로 도움이 된다)를 0/1로 라벨한다. 타당하지만 뻔한 연결은 새로움 0이다 | 델타브레인 품질 = 세 축이 모두 1인 창발 엣지 비율 |
| HUMAN-02 | G1·G2는 수용 가능한 다리의 예시다. 나오면 L2 라벨 대상이고, 나오지 않았다고 실패는 아니다 | 합성 프로토콜 점검용 |
| HUMAN-03 | 중단 조건: dogfooding 질의 10건 중 HUMAN-01 품질 0.3 미만이 절반을 넘으면 매칭이나 합성을 다시 설계한다 | PROJECT.md 중단 조건 |

### 5.4 매칭 — 키워드를 무시하지 않는다

| ID | 입력/상황 | 기대 결과 | 금지 결과 | 중요도 |
|---|---|---|---|---|
| MUST-M1 | 질의 Q-01 | 반환되는 모든 서브브레인의 관련도가 τ(`config/matching.json`) 이상이다. 서브브레인마다 매칭 근거(겹친 용어)와 관련도를 함께 돌려준다. 무관한 D는 없다 | τ 미만 서브브레인, 근거 없는 반환 | Must |
| MUST-M3 | 질의 Q-02 (주제 없음) 또는 `query_mode=whole_host` | 호스트 서브브레인 전체(태그·라벨)를 질의 용어로 쓴다. 결과에 `query_mode_used=whole_host`가 표시된다. D는 없다 | 질의 문장 단어("두뇌", "평가")로 매칭 | Must |
| NEVER-08 | 질의 Q-03 (관련 서브브레인 없음) | `NO_RELEVANT_SUBBRAIN`. 커널을 만들지 않고 사용량도 차감하지 않는다 | 개수를 채우려고 무관한 서브브레인을 끼움 | Must |
| MUST-M4 | 어떤 질의든 | 후보는 **다른 사용자의 공개** 서브브레인 최신 버전뿐이다. 호스트 본인의 서브브레인과 비공개 서브브레인은 후보가 아니다 | 본인·비공개 서브브레인 포함 | Must |
| PROV-M2 | 다양성 전략 `relevance_plus_diversity` | 호스트와 도메인이 겹치지 않는 후보가 τ 이상으로 있으면 1개 이상 포함한다 | — | **잠정** — 오너가 기준을 정할 때까지 기본 전략. `relevance_only`로 바꿀 수 있다 |

### 5.5 서브브레인 노출 금지

| ID | 입력/상황 | 기대 결과 | 금지 결과 |
|---|---|---|---|
| NEVER-01 | 사용자 B의 비공개 서브브레인을 사용자 A가 search, get, canal_open, 또는 **ID로 직접 호출** | 결과 0건. 존재하지 않는 ID와 똑같은 응답(`NOT_FOUND`) | B 데이터 반환, 다른 응답으로 존재 노출 |
| NEVER-02 | 공개 → 비공개로 전환한 서브브레인 | 검색과 **새** 커널에서 즉시 제외. 기존 커널의 `canal_get`에서도 내용이 빠진다. **기존 델타브레인** 안의 파생 노드는 유지되고 그 커널 참여자는 계속 본다. 주인은 자기 목록에서 계속 본다 | 새 커널 등장, 기존 델타브레인에서 사라짐, 주인 목록에서 사라짐 |
| NEVER-03 | 어떤 사용자용 도구에도 "삭제"가 없다. 서버는 모든 버전을 보관한다 | 도구 목록에 삭제 동작 없음. 비공개로 바꿔도 DB 행은 남는다 | 사용자가 행을 지울 수 있음 |
| NEVER-04 | 원문 청크, `source_url`, 로컬 경로(`C:\`, `/Users/`, `/home/`), 이메일, 전화번호가 든 가져오기 원본 | 가져올 때 허용 필드 밖은 버리고, 남은 텍스트의 경로·이메일·전화번호는 가린다. 무엇을 가렸는지 보고한다. 가져온 직후 상태는 **비공개**다. 공개하려면 미리보기의 `content_hash`를 확인값으로 보내야 한다 | 그대로 저장되거나 곧바로 공개 |
| NEVER-05 | 커널 참여자가 아닌 사용자 C가 그 커널이나 델타브레인 ID를 직접 호출 | `NOT_FOUND` | 반환 |
| NEVER-11 | 기존 델타브레인에서, 지금은 비공개인 서브브레인에서 온 노드·참조를 그 서브브레인 주인이 **아닌** 참여자가 볼 때 | 주인 식별자 자리에 `"비공개 기여자"`와 **암호화된 토큰**만 보인다. 토큰은 서버 키로만 복호화되고, 같은 델타브레인 안에서는 같은 값, 다른 델타브레인끼리는 다른 값이다 | 주인 ID·이름이 평문으로 보임 |

## 9. 플래너 추가 — 오너 확인 대기

검증기를 구현 가능하게 만들려고 플래너가 넣은 항목이다. 오너가 승인하지 않은 기준을 몰래 넣지 않도록 따로 표시한다.

| 항목 | 이유 |
|---|---|
| 질의 노드는 출처 규칙에서 면제 (§4) | 없으면 MUST-Q1과 Q2가 서로 모순된다 |
| `source` 노드 = 참조 1개 + 라벨 일치 (MUST-Q9, `SOURCE_MISMATCH`) | 없으면 출처를 쉽게 위조할 수 있다 |
| `PROVENANCE_INVALID`, `QUERY_NODE_COUNT`, `SCHEMA_INVALID` 코드 분리 | 합성기가 무엇을 고쳐야 하는지 알 수 있게 |
| 창발 = 유효 출처 주인 2명 이상 (§4) | 오너 정의 "서로 다른 주인의 서브브레인을 잇는"을 계산 가능하게 |
| `applies_when` 필드 권장 (L1 강제 아님) | self-test 1 "때에 따라서는" — 연결이 성립하는 조건을 남긴다 |
| MUST-C1 호스트 서브브레인 공개 필수 | Q3 대칭 동의를 실제로 강제 |
| MUST-C2 호스트만 제출 | 참여자는 받기만 한다 |
| NEVER-11의 토큰 = 델타브레인별 결정적 암호화 | "암호화"를 한 가지 방식으로 고정 |
| NEVER-12 fail closed | 형제 프로젝트는 토큰이 없으면 기본 범위로 열린다. 그 패턴을 따르지 않는다 |

## 10. 변경 규칙

1. 기준 변경을 별도 변경으로 제안한다.
2. 오너가 근거를 확인해 승인한다.
3. 새 버전이 고정된 뒤에 구현을 바꾼다.
4. 테스트가 실패했다고 기준을 고치지 않는다.
