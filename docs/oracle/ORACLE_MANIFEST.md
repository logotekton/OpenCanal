# Oracle Manifest — opencanal v0

> NDSH 부록 B-4 양식. 이 문서가 v0의 정답 기준이다.
> **Builder(코드를 쓰는 에이전트)는 이 문서를 수정할 수 없다.** 기준을 바꾸려면 먼저 오너가 이 문서의 변경을 따로 승인해야 한다.

- 대상: opencanal v0 (R0, 로컬, 합성 두뇌)
- 버전: 2026-10-06.1 (초안)
- 승인자·시각: 오너 — **미승인** (아래 Owner self-test를 마치면 승인)
- Builder 수정 가능: 아니오

## 품질 판정은 세 층으로 한다

델타브레인 품질이 제품의 핵심이다. 그래서 판정자 하나에 맡기지 않는다 (NDSH 12장 "여러 판정자를 조합한다").

| 층 | 판정자 | 하는 일 | 실패하면 |
|---|---|---|---|
| L1 결정론 검증 | 서버의 `canal_submit` 검증기 | 구조, 출처, 질의 연결, 새로움, 금지어를 검사한다 | **제출 거부**. 이유 코드를 돌려준다 |
| L2 사람 라벨 | 오너 | 창발 엣지마다 새로움·타당성·쓸모를 라벨한다 | 매칭이나 합성 프로토콜을 다시 설계한다 |
| L3 LLM Judge | 보조 판정 | L2 라벨과 일치도를 먼저 잰다. 일치도가 기준을 넘을 때만 보조로 쓴다 | v0에서는 쓰지 않는다 |

L1을 통과했다고 좋은 델타브레인인 것은 아니다. L1은 **명백히 무의미한 것을 걸러내는 하한**이다. 진짜 품질은 L2가 판정한다.

### 델타브레인 품질 — L1 결정론 검증 (제출 시 서버가 거부)

| ID | 검사 | 거부 코드 |
|---|---|---|
| MUST-Q1 | 모든 노드·엣지에 출처가 있고, 출처는 **이번 커널에서 연** 서브브레인 버전의 실제 노드를 가리킨다. 새로 만든 노드는 근거 노드를 2개 이상 인용한다 | `PROVENANCE_MISSING` / `PROVENANCE_OUT_OF_CANAL` |
| MUST-Q2 | 질의 노드가 정확히 1개 있고, 모든 노드가 질의 노드에서 3홉 안에 있다 | `OFF_QUERY_NODE` |
| MUST-Q3 | 창발 엣지(출처 주인이 서로 다른 노드를 잇는 엣지)가 1개 이상 있고, 그중 1개 이상은 **호스트 서브브레인**에 닿는다 | `NO_EMERGENCE` / `HOST_NOT_TOUCHED` |
| MUST-Q4 | 엣지 관계는 통제 어휘 안에서만 쓴다 (아래 표). 창발 엣지에는 `rationale`(40~400자)이 반드시 있다 | `RELATION_NOT_ALLOWED` / `RATIONALE_MISSING` |
| MUST-Q5 | 새 노드의 정규화된 라벨이 입력 서브브레인의 기존 라벨과 같지 않다. 창발 엣지의 (source, target) 쌍이 입력 서브브레인에 이미 있지 않다 | `NOT_NOVEL` |
| MUST-Q6 | 노드 라벨이 금지 일반어만으로 이뤄지지 않는다 (금지어 목록 `fixtures/quality/generic_terms.txt`, 오너가 관리) | `GENERIC_LABEL` |
| MUST-Q7 | 창발 엣지의 `rationale`이 서로 복사본이 아니다 (정규화 후 같은 문장 비율 20% 이하) | `TEMPLATED_RATIONALE` |
| MUST-Q8 | 크기 상한: 노드 60개 이하, 엣지 120개 이하 | `TOO_LARGE` |

**엣지 관계 통제 어휘 (v0):**

| 관계 | 뜻 |
|---|---|
| `applies_to` | A의 방법·원리를 B의 문제에 적용할 수 있다 |
| `analogous_to` | 구조가 대응한다 (무엇이 무엇에 대응하는지 rationale에 쓴다) |
| `contradicts` | A가 B의 전제나 결론을 반박한다 |
| `extends` | A가 B를 확장하거나 일반화한다 |
| `requires` | A가 성립하려면 B가 필요하다 |
| `alternative_to` | A가 B를 대체할 수 있다 |
| `explains` | A가 B의 원인·기제를 설명한다 (인과를 단정하지 않는다) |
| `risk_for` | A가 B의 실패·위험 요인이 된다 |

**금지:** `related_to`, `관련있다`, `연결된다`, `시너지` 같은 무내용 관계.

## Owner self-test — 오너가 직접 판정할 5건

구현 설명 없이 오너가 판정한다. 답이 나오면 이 문서를 승인 버전으로 고정한다.

| # | 종류 | 상황 | 오너 판정 |
|---|---|---|---|
| 1 | 정상 | Q-01에 대해 G1이 나온 델타브레인. 이 연결이 "쓸모 있다"에 해당하는가? | |
| 2 | 정상 | 호스트 A, 질의 Q-01에서 B·C가 붙고 A2·D가 빠졌다. 맞는 매칭인가? | |
| 3 | 경계 | 질의 Q-02 "내 두뇌를 평가해줘"처럼 주제가 없는 질의에서 관련도는 무엇을 기준으로 재야 하는가? (호스트 서브브레인 전체 / 거부 / 다른 방식) | |
| 4 | 경계 | 창발 엣지가 딱 1개이고 타당하지만 뻔하다면 (예: "BIM `requires` 데이터 표준") 수락할까 거부할까? L1은 수락한다. L2에서 0점 처리로 충분한가? | |
| 5 | 금지 | 철회한 서브브레인의 파생 노드가 기존 델타브레인에 남는다. 이때 **철회한 사람의 이름(주인 표시)**도 계속 보여야 하는가? | |

- 미해결 정책: Owner self-test 3·5, 임계값 τ의 초기값
- Builder 전달 판정: **부분 READY** — NEVER 항목, MUST-Q1~Q8, MUST-M1~M2, 티어 게이트는 바로 구현할 수 있다. HUMAN 기준과 Q-02 처리 방식은 self-test 뒤에 고정한다

## 변경 규칙

1. 기준 변경을 별도 변경으로 제안한다.
2. 오너가 근거를 확인해 승인한다.
3. 새 버전이 고정된 뒤에 구현을 바꾼다.
4. 테스트가 실패했다고 기준을 고치지 않는다.
