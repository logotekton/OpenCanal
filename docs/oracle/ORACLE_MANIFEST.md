## 3. 품질 판정은 세 층으로 한다

| 층 | 판정자 | 하는 일 | 실패하면 |
|---|---|---|---|
| L1 결정론 검증 | 서버의 `canal_submit` 검증기 | 구조, 출처, 질의 연결, 창발, 새로움, 금지어를 검사한다 | **제출 거부.** 모든 위반을 이유 코드와 함께 한 번에 돌려준다 |
| L2 사람 라벨 | 오너 (`deltabrain_rate`) | 창발 엣지마다 새로움·타당성·쓸모를 0/1로 라벨한다 | 매칭이나 합성 프로토콜을 다시 설계한다 |
| L3 LLM Judge | 보조 | L2 라벨과 일치도를 먼저 잰다 | v0에서는 쓰지 않는다 |

L1은 **명백히 무의미한 것을 걸러내는 하한**이다. L1을 통과했다고 좋은 델타브레인인 것은 아니다.

## 4. 델타브레인 구조 정의 (검증기가 기대하는 모양)

- 노드 `kind`
  - `query`: 질의 노드. 정확히 1개. **출처 규칙에서 면제된다.**
  - `source`: 입력 서브브레인의 노드를 앵커로 가져온 것. 출처 정확히 1개. 라벨은 인용한 노드의 라벨과 같아야 한다.
  - `new`: 합성기가 만든 노드. 출처 2개 이상.
- 출처 참조 `ProvRef` = (`subbrain_id`, `version`, `node_id`)
- 노드의 **주인 집합** = 그 노드가 인용한 (유효한) 출처의 주인 집합. 엣지의 **주인 집합** = 양 끝 노드 주인 집합의 합집합
- 엣지에 직접 적은 출처는 **근거**다. MUST-Q1로 유효성만 검사하고, 창발·호스트 판정에는 쓰지 않는다 (v.3)
- **다리(bridge)** = 주인 집합에 주인이 **2명 이상**인 `new` 노드. **호스트 다리** = 호스트 서브브레인을 인용하는 다리 (v.8)
- **창발 엣지** = 다음을 모두 만족하는 엣지 (v.8)
  - 주인 집합에 주인이 2명 이상이다
  - 양 끝 어느 쪽도 `query` 노드가 아니다
  - `new` 노드 N과 `source` 노드 S를 잇는데 S가 인용한 노드가 이미 N의 출처에 들어 있는 경우(**자기 앵커 엣지**)가 아니다
  - (`new`–`new` 엣지는 위 조건을 만족하면 창발이다)
- **호스트에 닿는 엣지** = 양 끝 노드 중 하나가 호스트 서브브레인을 인용하는 엣지
- **평가 단위(다리 단위)** = 다리 노드 ∪ 창발 엣지 (v.8)

## 5. 핵심 기준표

### 5.1 델타브레인 품질 — L1 결정론 검증

| ID | 검사 | 거부 코드 |
|---|---|---|
| MUST-Q1 | `query`를 뺀 모든 노드에 출처가 있다. 모든 참조는 **이번 커널에 들어간** 서브브레인 버전을 가리키고, 그 버전에 실제로 있는 노드를 가리킨다. `new` 노드는 참조가 2개 이상이다 | `PROVENANCE_MISSING` / `PROVENANCE_OUT_OF_CANAL` / `PROVENANCE_INVALID` |
| MUST-Q2 | `query` 노드가 정확히 1개 있고, 모든 노드가 질의 노드에서 무방향 3홉 안에 있다 | `QUERY_NODE_COUNT` / `OFF_QUERY_NODE` |
| MUST-Q3 | 다리와 창발 엣지를 합쳐 1개 이상 있고, 그중 1개 이상은 호스트에 닿는다(호스트 다리, 또는 호스트에 닿는 창발 엣지) (v.8) | `NO_EMERGENCE` / `HOST_NOT_TOUCHED` |
| MUST-Q4 | 엣지 관계는 통제 어휘(§5.2)만 쓴다. **평가 단위마다 설명이 있다** (v.8): 창발 엣지에는 `rationale`(정규화 후 40~400자), 다리 노드에는 `summary`(정규화 후 40~600자) | `RELATION_NOT_ALLOWED` / `RATIONALE_MISSING` (node_id 또는 edge_id 표시) |
| MUST-Q5 | `new` 노드의 정규화 라벨이 커널 입력 서브브레인의 어떤 라벨과도 같지 않다. 양 끝이 `source`인 엣지는 (창발 여부와 무관하게, v.3) 입력 서브브레인에 이미 있는 엣지(같은 두 노드, 방향 무관)를 그대로 옮긴 것이 아니다 — 델타브레인에는 차이만 담는다 | `NOT_NOVEL` |
| MUST-Q6 | `new` 노드 라벨이 금지 일반어(`config/generic_terms.txt`)만으로 이뤄지지 않는다 | `GENERIC_LABEL` |
| MUST-Q7 | 평가 단위(다리 노드의 `summary`, 창발 엣지의 `rationale`) 중 정규화한 설명이 다른 단위와 똑같은 단위의 비율이 20% 이하다 (v.8: 다리 요약 포함). 비교 전에 rationale 안의 **양 끝 노드 라벨**(정규화)을 같은 자리표시자로 바꾼다 — 라벨만 갈아 끼운 틀 문장도 같은 문장이다 (v.4) | `TEMPLATED_RATIONALE` |
| MUST-Q8 | 노드 60개 이하, 엣지 120개 이하 | `TOO_LARGE` |
| MUST-Q9 | `source` 노드의 라벨이 인용한 노드의 라벨과 정규화 기준으로 같다 | `SOURCE_MISMATCH` |
| MUST-Q0 | 스키마: 노드 ID 중복 없음, 엣지 양 끝이 존재하는 노드, 필수 필드 존재 | `SCHEMA_INVALID` |

**정규화** = 유니코드 NFKC, 보이지 않는 문자(서식 문자 Cf, 한글 채움 문자, 이형 선택자)와 구두점을 공백으로, 소문자, 연속 공백을 하나로, 앞뒤 공백 제거. (v.4: 보이지 않는 문자 추가)

### 5.2 엣지 관계 통제 어휘 (v0)

| 관계 | 뜻 |
|---|---|
| `applies_to` | A의 방법·원리를 B의 문제에 적용할 수 있다 |
| `analogous_to` | 구조가 대응한다 (무엇이 무엇에 대응하는지 rationale에 쓴다) |
| `contradicts` | A가 B의 전제나 결론을 반박한다 |
| `extends` | A가 B를 확장하거나 일반화한다 |
| `requires` | A가 성립하려면 B가 필요하다 |
| `alternative_to` | A가 B를 대체할 수 있다 |
| `explains` | A가 B의 원인·기제를 설명한다 (인과를 단정하지 않는다) |
| `risk_for` | A가 B의 실패·위험 요인이 된다 |

`related_to`, `관련있다`, `연결된다`, `시너지` 같은 무내용 관계는 어휘에 없으므로 `RELATION_NOT_ALLOWED`다.

### 5.3 델타브레인 품질 — L2 사람 라벨

| ID | 기준 | 판정 |
|---|---|---|
| HUMAN-01 | **평가 단위(다리 노드와 창발 엣지)**마다 **새로움**(내 두뇌만으로는 안 나왔을 연결), **타당성**(설명이 말이 된다), **쓸모**(질의에 실제로 도움이 된다, 현실 제약 포함)를 0/1로 라벨한다. 타당하지만 뻔한 연결은 새로움 0이다 (v.8: 엣지 → 다리 단위) | 델타브레인 품질 = 세 축이 모두 1인 평가 단위 비율 |
| HUMAN-02 | G1·G2는 수용 가능한 다리의 예시다. 나오면 L2 라벨 대상이고, 나오지 않았다고 실패는 아니다 | 합성 프로토콜 점검용 |

### 5.4 매칭 — 키워드를 무시하지 않는다

| ID | 입력/상황 | 기대 결과 | 금지 결과 | 중요도 |
|---|---|---|---|---|
| MUST-M1 | 질의 Q-01 | 반환되는 모든 서브브레인의 관련도가 τ(`config/matching.json`) 이상이다. 서브브레인마다 매칭 근거(겹친 용어)와 관련도를 함께 돌려준다. 무관한 D는 없다 | τ 미만 서브브레인, 근거 없는 반환 | Must |
| MUST-M3 | 질의 Q-02와 그 변형 Q-02a~d (주제 없음) 또는 `query_mode=whole_host` | 호스트 서브브레인 전체(태그·라벨)를 질의 용어로 쓴다. 결과에 `query_mode_used=whole_host`가 표시된다. D는 없다 | 질의 문장 단어("두뇌", "평가", "만든")로 매칭, 또는 주제 없는 질의가 `NO_RELEVANT_SUBBRAIN`으로 끝남 | Must |
| MUST-M5 | 호스트와 후보 사이의 거리 (v.6 오너 결정 "내용으로 계산", v.7 정의 변경) | **유사도 = 호스트 낱말 중 후보도 가진 낱말의 비율** = \|H ∩ C\| ÷ \|H\|. H와 C는 각 서브브레인(호스트는 커널에 쓰는 버전, 후보는 공개 버전)의 **노드 라벨과 태그**에서 `textnorm.tokenize`(조사 제거, 불용어 제거)로 만든 **서로 다른 낱말의 집합**이다. 요약, 노드 유형, 엣지, 제목, 신고한 분야(`domains`)는 쓰지 않는다. **거리 = 1 − min(1, 유사도 ÷ `distance_saturation`)**. H가 비면 거리 1. 계산은 정확해야 하고(유리수), 결과는 결정적이다. 후보가 호스트와 겹치지 않는 낱말을 아무리 덧붙여도 거리는 변하지 않는다 | 낱말 채우기·반복으로 거리를 키울 수 있음, 신고한 분야나 제목으로 거리가 바뀜 | Must |

## 9. 플래너 추가 — 오너 확인 대기

검증기를 구현 가능하게 만들려고 플래너가 넣은 항목이다. 오너가 승인하지 않은 기준을 몰래 넣지 않도록 따로 표시한다.

|---|---|
| 질의 노드는 출처 규칙에서 면제 (§4) | 없으면 MUST-Q1과 Q2가 서로 모순된다 |
| `source` 노드 = 참조 1개 + 라벨 일치 (MUST-Q9, `SOURCE_MISMATCH`) | 없으면 출처를 쉽게 위조할 수 있다 |
| `PROVENANCE_INVALID`, `QUERY_NODE_COUNT`, `SCHEMA_INVALID` 코드 분리 | 합성기가 무엇을 고쳐야 하는지 알 수 있게 |
| 창발 = 유효 출처 주인 2명 이상 (§4) | 오너 정의 "서로 다른 주인의 서브브레인을 잇는"을 계산 가능하게 |
| `applies_when` 필드 권장 (L1 강제 아님) | self-test 1 "때에 따라서는" — 연결이 성립하는 조건을 남긴다 |

| MUST-C2 호스트만 제출 | 참여자는 받기만 한다 |
| NEVER-11의 토큰 = 델타브레인별 결정적 암호화 | "암호화"를 한 가지 방식으로 고정 |
| NEVER-12 fail closed | 형제 프로젝트는 토큰이 없으면 기본 범위로 열린다. 그 패턴을 따르지 않는다 |
| (v.3) 창발·호스트 판정은 양 끝 노드의 출처로만 | v.2에서는 같은 주인의 두 노드를 잇는 엣지에 남의 노드 출처 하나만 붙여도 창발로 셌다. 이 빈틈을 막는다. 남의 노드를 인용한 `new` 노드를 거치는 정상적인 다리는 그대로 창발이다 |
| (v.3) MUST-Q5 엣지 조항을 모든 source–source 엣지로 확대 | 창발 판정을 양 끝 노드로만 하면 같은 서브브레인 안의 엣지는 창발이 될 수 없어 v.2 조항이 쓸모없어진다. 입력 엣지를 그대로 옮긴 엣지는 새 정보가 없으므로 창발 여부와 무관하게 거부한다 |
| (v.3) `ErrorCode.INTERNAL` | 예상하지 못한 서버 오류의 envelope 코드. 내부 정보(스택 등)는 담지 않는다 |
| (v.4) 정규화에 보이지 않는 문자 추가 | 한글 채움 문자 등이 rationale 길이를 부풀리고 라벨 비교를 피해 가는 것을 막는다 (적대 검토 L1-2, SAN-4) |
| (v.4) MUST-Q7 비교 전 양 끝 라벨 치환 | 라벨만 바꾼 틀 문장이 정확 일치 비교를 피해 간다 (L1-5 중 결정적 부분만) |
| (v.4) MUST-M3 변형 질의 Q-02a~d | 자연스러운 존대·띄어쓰기 변형이 TOPIC으로 잘못 판정되어 "만든" 같은 낱말로 커널이 열렸다 (MATCH-2). 불용어 추가로 고친다 |
| (v.4) NEVER-02 호스트 포함 | D-007 대칭 동의에서 이미 따라 나온다 (TS-1) |
| (v.4) NEVER-04 주민등록번호·비밀값·ID 필드·정규화 후 마스킹 | 실데이터에서 주민등록번호가 실제로 나온 적이 있다 (오너의 다른 프로젝트). 전각 문자로 우회됐다 (GAP-1, SAN-1~6) |
| (v.4) NEVER-09 범위 명시 | 호스트가 정한 엣지 ID, 표시 이름, 매칭 용어도 남이 쓴 문자열이다 (EXP-4) |
| (v.5) `distance_bonus` = 0.3 | 오너는 "가산점"만 정했다. Q-01에서 같은 관련도(0.40)의 먼 분야(B·C)가 가까운 분야(A2, 0.56)를 넘도록 0.3을 골랐다. 주제 없는 질의(Q-02)에서는 A2(1.00)가 여전히 위다 |
| (v.8) 다리·창발 재정의 | 첫 LLM 합성 6건에서 창발 엣지가 전체의 94~100%였다(질의 엣지·자기 앵커 엣지 포함). 새 정의로 다시 세면 델타브레인마다 창발 엣지 1~7개, 다리 4~5개이고 6건 모두 MUST-Q3을 통과한다. `new`–`new` 엣지는 두 다리 사이의 관계라 출처를 되풀이하는 것이 아니어서 창발로 센다 |
| (v.8) 다리 노드에 요약 필수 | 오너는 다리를 요약과 엣지 설명으로 판단했다. 같은 개념도 서술의 구체성에 따라 0/0/0~1/1/1로 갈렸다 (HUMAN-001 §3). 설명 없는 단위는 평가할 수 없다 |
| (v.8) 평가 도구 `deltabrain_rate`의 대상 = 다리 노드 또는 창발 엣지 (`target_id`), 아니면 `NOT_RATEABLE` | 평가 단위 변경. 엣지 단위 품질은 합성기가 그린 엣지 수에 따라 흔들렸다 (R1 0.40 vs 0.28) |
| (v.8) 다리 노드의 `constraints` | 현실 제약 검토(비용·제작 공수·공정·운영과 그 대가, 적용 조건). 오너 결정에 따라 L1 거부 사유가 아니다. 통계 `bridges_with_constraints`로 채운 수를 보고한다 |
| (v.7) 거리 = 호스트 낱말 겹침 비율 (라벨·태그) | v.6 코사인은 관계없는 낱말 하나를 반복해 채우면 후보가 스스로 거리를 키워 가산점과 먼 후보 자리를 차지할 수 있었다 (적대 검토 M5-PAD-1, 확인). 호스트 기준 비율은 덧붙인 낱말에 영향을 받지 않는다. 요약은 "된다·한다" 같은 서술 낱말이 섞여 같은 분야와 먼 분야의 구분을 흐려서 뺐다 (fixture: 라벨·태그만 쓰면 A2 0.278, B·C 0.056, D·X 0) |
| (v.6) `distance_saturation` = 0.25, `far_distance` = 0.5 — v.6 코사인 기준으로 고른 값이며 v.7에도 그대로 쓴다 (아래 수치는 v.6 코사인 기준, v.7 수치는 위 행) | 낱말 겹침은 같은 분야끼리도 낮아서(fixture에서 A–A2 코사인 0.34) 그대로 쓰면 거리가 0.66~1.0에 몰리고 가산점이 거의 작동하지 않는다. 유사도 0.25 이상을 "같은 분야"로 본다. 기본값에서 Q-01은 B·C(거리 약 0.75·0.81)가 A2(거리 0)보다 위다. 내용 거리에서는 정확히 1.0이 드물어 다양성 보장의 "먼 후보" 기준을 0.5로 둔다 |
| (v.6) 반올림 전 값으로 비교 | 두 번 반올림하면 점수 순서와 관련도 동점 처리가 틀어졌다 (적대 검토 M2-ROUND-1) |
| (v.6) 백업 임시 파일 0600 | 백업이 평문 DB 사본을 0644로 잠깐 만들었다 (적대 검토 E3-3) |
| (v.5) `canal_get` 비공개 항목 위치 | 비공개 항목이 원래 순위 자리에 남으면 순서로 점수·ID 순서가 드러나 커널끼리 엮을 수 있었다 (적대 검토 N11-V5-ORDER-1) |
| (v.5) `canal_get` 비공개 항목의 `withheld_ref` | "엮을 수 없게"를 구현하는 방식. 커널 안에서만 같은 값 |
| (v.4) NEVER-11 통계로 재식별 금지 | 관여 주인 수와 창발 판정 차이로 비공개 기여자가 누군지 확정할 수 있었다 (EXP-1) |

## 11. 변경 규칙

1. 기준 변경을 별도 변경으로 제안한다.
2. 오너가 근거를 확인해 승인한다.
3. 새 버전이 고정된 뒤에 구현을 바꾼다.
4. 테스트가 실패했다고 기준을 고치지 않는다.
